# GraphRAG over SEC 10-K filings: Phase Plan

Each phase ends with something you can **run and see**. Don't start a phase until the previous
one works. Exception: the long extraction run (Phase 8) continues in the background while
Phases 5–7 are built, once the development slice exists (see Phase 4).

## The core problem in one paragraph
Having an LLM read all ~38M tokens once would take ~6 months on the free API (200K tokens/day),
and weeks even with the Claude workaround. So the plan is built around **spending LLM tokens only
where they add value**:
- Do everything that doesn't need an LLM (structure, chunking, embeddings) without one.
- Skip text we've already processed. 10-Ks repeat a lot from year to year, so we only send
  *new or changed* paragraphs to the LLM.
- Make the pipeline resumable and budgeted, so it can run for weeks without wasting quota.

## Phase 2: Structural graph + vector baseline (no LLM) ✅ Completed 2026-11-25
**Goal:** a working plain RAG system, used as the baseline to compare against.
- Structural graph straight from metadata: `Company → Filing → Section → Chunk`
- Chunking strategy (section-aware, sized for both embedding and extraction)
- Embed every chunk locally and store in a Neo4j vector index
- Simple vector-search Q&A

**You'll learn:** chunking trade-offs; how much you get "for free" without any LLM extraction.

## Phase 3: Graph schema + extraction prototype ✅ Completed 2026-11-26
**Goal:** decide *what* the graph holds, and test LLM extraction on a few filings.
- Schema built for your question types: relationships (competitors, suppliers, customers,
  partners), risks, products/segments and themes, all tagged with the fiscal year
  (for change over time)
- **Cheap extraction tiers first (no LLM), run on every chunk:**
  - *Tier 2, pattern/dictionary:* match our 130 known companies (names, tickers) and
    phrases like "competitors include…" → `MENTIONS` edges
  - *Tier 3, local NLP model* (e.g. spaCy or GLiNER): find other companies, products and places
- **Use tiers 2–3 as a filter:** only chunks likely to hold a relationship (e.g. 2+ entities)
  go to the LLM; boilerplate is skipped. Measure how much LLM usage this saves.
- Extraction prompt with a strict output format (schema-guided), using LlamaIndex
- Run it on ~3 filings, inspect the results by hand, iterate on the prompt
- Measure **tokens per chunk** to get a real full-corpus cost estimate

**You'll learn:** schema-guided vs free-form extraction; why the schema follows from the questions;
the tiered "cheapest method that's good enough" approach (structure → patterns → local NLP → LLM).

## Phase 4: Production ingestion pipeline ✅ Completed 2026-11-26
**Goal:** the full-corpus pipeline, built properly. Each step is one stage of the pipeline, in the
order data flows through it (so the pipeline diagram follows this list):

```
manifest → 4.1 planner → 4.2 job store → 4.3 batcher → 4.4 router → 4.5 worker → 4.6 graph writer
                                                                         ↓
                                                             4.7 progress + alerts
```
- ✅ **4.1 Work planner:** pick a wave of filings from `manifest.csv` (in priority order: the
  development slice comes first, see below). For each filing, build its work items: new risk
  titles (route A) and new or flagged chunks (route B). **Change detection** happens here: text
  unchanged from the previous year never becomes a work item
- ✅ **4.2 Job store:** every work item gets a status (pending / running / done / failed) and an
  attempt count, saved to disk, so a crash or sleep resumes where it stopped (**resumable**)
- ✅ **4.3 Batcher:** groups pending items into requests (50 titles per route-A call, 8 chunks per
  route-B call; 25 / 4 on Groq), one company per batch, across its fiscal years, so the prompt
  overhead is paid once per batch
- ✅ **4.4 Backend router:** backends run **in parallel**, each on whole companies (taxi rank:
  a free backend claims the next company in priority order and keeps it). Gates per backend:
  Groq daily budget (per API key), Antigravity 5-hour ≥ 95% / weekly ≥ 90%, Sonnet schedule
  (night + weekly < 75%; daytime only with the user's allowance; never at weekly ≥ 90% unless
  overridden)
- ✅ **4.5 Worker:** sends the batch (through the **LLM cache**, never pay twice), validates the
  answer, **retries** with backoff on errors, then marks items done or failed (with the reason
  logged). Re-running a finished batch costs nothing (**idempotent**)
- ✅ **4.6 Graph writer:** loads validated facts into Neo4j, linked to their chunk and fiscal year.
  Uses merge-style writes so re-runs never create duplicates
- ✅ **4.7 Progress + alerts:** per-batch log, totals, ETA; push events (gates, company done, errors,
  hourly summary, run stopped); one status command
- ✅ **4.8 Run skills:** `/extract-run`, `/extract-sonnet`, `/extract-status`, invocable only by the
  user; every runner start under `caffeinate -i`; graceful stop by SIGINT/SIGTERM
- ✅ **4.9 First wave:** PANW CRWD TENB RPD QLYS × first 2 years end to end (started by the
  user), checked by hand, loaded into Neo4j
- ✅ **4.9 Tuning + freeze:** prompt v4 → v6, schema v1 → v3 (new risk categories, `INTEGRATES_WITH`,
  no "Item 1A" titles), `jobs replan` for selective re-extraction, per-account Groq budget;
  **schema v3 / prompt v6 frozen**
- ✅ **4.10 Stop-when-blocked:** `/extract-run` stops each backend when its limits block it; the
  user restarts it once they are restored
- ✅ **4.11 `--with-sonnet`:** opt-in Sonnet runner from `/extract-run` (also stop-when-blocked)

**You'll learn:** idempotency, backpressure, and how real ingestion survives crashes and limits.

### Milestone: development slice → start Phases 5–7 in parallel
The full-corpus extraction takes weeks, so later phases don't wait for it. Once Phase 4 works
(4.9 done), the runner extracts a **development slice** first, then keeps going in the background
(Phase 8) while we build Phases 5–7 on the data that exists.
- **Slice (proposed, 17 companies, all years):** the security group PANW CRWD TENB RPD QLYS FTNT
  ZS OKTA NET S VRNS + the companies they name most: MSFT GOOGL GEN CRM ORCL NOW. Covers every
  question type: relationships between corpus companies, multi-hop, cross-company and change
  over time. ~138 filings left; **≈3.3M LLM tokens** (measured on wave 1), about **6–7 days**
  with Groq + Antigravity, ~4–5 with Sonnet nights (the earlier "1–2 days" was too optimistic)
- **"Sufficient data" = the slice is done** and spot-checked
- **Rule for Phases 5–7:** their steps must be **re-runnable** as new filings arrive (entity
  resolution merges new entities into existing ones; retrieval is never tuned to the slice only)
- **Watch memory:** the background run and our development share the 16 GB laptop

## Phase 5: Entity resolution
**Goal:** one node per real-world thing.
- "NVIDIA", "NVIDIA Corporation" and "Nvidia Corp." → one entity; link to `companies.csv` (CIK/ticker)
- Merge duplicate risks and themes using embeddings and rules

**You'll learn:** why entity resolution makes or breaks GraphRAG quality.

## Phase 6: Retrieval
**Goal:** answer all four question types.
- Hybrid retrieval: vector search + graph traversal + text-to-Cypher
- Time-aware queries (compare years)
- Cross-company queries (aggregate across the graph)
- Answers cite their sources (company, year, section)
- Compare against the Phase 2 baseline on a handful of questions

**You'll learn:** when graph retrieval beats vector search, and when it doesn't.

## Phase 7: FastAPI service
**Goal:** deployable API.
- `/query` endpoint, `/health`, ingestion status endpoint
- Config via environment variables, structured logging

## Phase 8: Full-corpus run (ongoing)
**Goal:** process all 950 filings (from `manifest.csv`) in waves until done.
- Run waves as quota allows, monitor progress, spot-check quality
